### 1.4 下次请求怎么生效

`binding.session.projections.faceOf("modelSelection")`（`client.js:1037`）。客户端侧会话句柄 API：`ctx.sessions.scope(sessionId)`、`ctx.sessions.binding(sessionId)`、`ctx.sessions.subagentAddress(sessionId)`（`client.js:1030-1037`）。

## 3. 有没有 per-session 的键值 / 元数据存储？

**没有专门的 per-session KV 服务。** 现有三条可用路径：

### (a) 会话事件 + Session projection（**推荐**，与模型选择、preset 同一套）

- 持久：写进会话 jsonl，重启/replay 自动重建；
- 隔离：天然按会话隔离；
- 语义：可被「会话复用/fork」显式处理（见下）；
- 代价：零 token、零缓存影响（投影不参与请求）。

最小示例（照 `agent-preset` 的写法）：

```js
// 1) 定义投影
export const workbenchProjectionDefinition = {
  key: 'workbench', stateVersion: 1,
  init: () => null,                                  // header 里没有这个字段，只能从事件来
  apply: (state, event) => event.type === 'workbench/selected' ? event.data.workbenchId : state,
  wire: { viewSchema, view: (state) => state },      // wire view 会同步给客户端
};

// 2) 注册 → 返回 handle（register 是可 await 的 thenable，resolve 出 { stateOf, readerFor, dispose }）
this.handle = await ctx.sessionProjections.register(workbenchProjectionDefinition);
const current = this.handle.stateOf(session);        // string | null

// 3) 写（会话日志事件，自动驱动投影）
session.append('workbench/selected', { workbenchId: 'frontend' });
```

- `register(definition)` 的返回值：`dsh-session-projection\lib\index.js:156-165` 的 `handle = { dispose, stateOf(session), readerFor(session) }`；`register` 本体在 `:84-113`（注释标为 legacy 兼容层，但 `agentPresets` 自己就这么用）。
- 参考实现：`dsh-agent-preset-registry\lib\types\session.js`（投影定义）、`lib\index.js:461`（`await ctx.sessionProjections.register(...)`）、`:478-480`（`presetForSession`）。
- 客户端读：`projections.faceOf(key)`（`dsh-api-session-controller\lib\client.js:1554` `faceOf(key) { return this.channel(key).face; }`）—— **`faceOf` 只在客户端**，host 侧用 `handle.stateOf(session)`。

### (b) `ctx.storageDomain`（`dsh-storage` + `dsh-storage-json` + `dsh-storage-domain`）

- 全局 KV，落 `~/.dsh/storages/**`，**重启保留**；
- 需要自己用 session id 当 key 做隔离；
- **不随会话删除**，不参与 fork/replay，冲突与清理要自己管。

```js
// 依赖：dsh-storage + dsh-storage-json(config.root) + dsh-storage-domain(config.backend: json)
const domain = await ctx.storageDomain.open(defineDomain({
  name: 'workbench', version: 1,
  tables: { selections: domainTable(z.object({ workbenchId: z.string() })) },
}));
ctx.effect(() => () => domain.close());
domain.table('selections').put(sessionId, { workbenchId: 'frontend' });
const row = domain.table('selections').get(sessionId);   // 同步读内存
```

代码位置：`dsh-storage-domain\lib\index.js:46`（`domainTable`）、`:61`（`defineDomain`）、`:381`（`open`）、`:190`（`table`）、`:254`（`get`）、`:270`（`put`）、`:296`（`update`）。局限：单进程可见、无跨表事务、无二级索引。

### (c) 会话创建 header（`meta`）

只有 `cwd / agentPreset / parentSession / isSeeded / origin / delegationDepth` 这类**建会话时确定**的字段（`dsh-session\lib\index.js:1066` 注释：「Detach, validate, and freeze the creation metadata published by a session」——**frozen**）。中途切换的工作台不能用它。

**结论**：工作台选择用 (a)。注意 fork/子会话**不会自动继承**最后一个事件 —— `agent-preset` 的做法就是在子会话里显式补写一条（`dsh-subagent\lib\types\manager.js:770` `child.session.append('agent-preset/selected', { agentPreset: ... })`）。工作台要在 fork 时同样补写。

## 4. `agentPreset` 运行时的真正来源

**会话头 jsonl 里的 `agentPreset` 只是初始值，恢复时不用它。** 权威来源是 Session projection `agentPreset`：

`dsh-agent-preset-registry\lib\types\session.js`（文件首注释原文）：

真正决定「用哪个 preset 跑」的路径（`dsh-api-session-controller\lib\types\agent.js`）：


**中途不可切换**（`registry\lib\index.js:766-777`）：

```js

  if (boundary.openTurnStartSeq !== null || boundary.lastTurn > 0)
    throw new RemoteError('agent-preset/locked', 'This session has already started', { sessionId: agent.id, agentPreset });
```

**前缀顺序（推断）**：provider 侧缓存前缀按 `tools → system → messages` 排列。DSH 未文档化服务端顺序，这条是由 `dsh-llm-deepseek\README.md` 的两句话反推的：system 的 in-history 改写能保住「through that history」的前缀，而 tool schema 改动会「prevent reuse **from the first altered token**」——若 tools 排在 messages 之后，改工具就不可能影响历史，这两句无法同时成立。**在该前提成立时：tools 段一变，messages 全部失效。** 另可反向验证：DSH 为「新增工具」专门做了 append + `defer_loading` + in-history `tool_addition` 的三件套，也只有「tools 在 messages 之前」才值得这么做。

### 5.3 缓存结论与代价

`dsh-llm-deepseek\README.md`（KV Cache effect，原文）：

> On a catalog entry declaring `systemPromptUpdate: in-history`, a system prompt change inside a continuing request series is appended after the cached history, so the prefix through that history stays reusable; **a tool-schema change still prevents reuse from the first altered token.**

`dsh-tools\README.md:171-173`：

> Prefix-stable while visible definitions and their order are unchanged. Registration, disposal, or scoped restriction may invalidate reuse from the first changed schema token.

模型能力（`dsh-llm-deepseek\lib\index.js:19-31`）：

| 模型 | `systemPromptUpdate` | `toolUpdate` |
|---|---|---|
| `deepseek-flash` | `in-history` | `addition-only` |
| `deepseek-v4-pro` | 未声明（undefined） | 未声明（undefined） |

**因此「中途改 tools 集合 = 前缀缓存全失效」在多数场景成立，但有一个例外：**

1. **只新增工具（不删、不重排）+ `addition-only`**：新工具 append 到 tools 末尾且 `defer_loading: true`，同时在 messages 里追加 `tool_addition` 引用 → 已缓存前缀（system + 原有 tools + 到声明点的历史）仍可复用。这是 DeepSeek 上唯一「便宜」的切换方向。
2. **删除工具**：`addition-only` 会把它从 declarations 中物理删掉 → tools 段内容变化 → **整段历史 miss**。
3. **重排工具**：同上，全 miss（`dsh-system-prompt\README.md:166`：「reordering changes cache shape but not semantic content」）。
4. **`deepseek-v4-pro`（无 toolUpdate 声明）**：任何增删都全量重发 → 全 miss。
5. 换模型/路由、换 system prompt（非 in-history 模型）、改任一保留工具的 schema 文本，同样从第一个改动 token 起失效（`dsh-agent-loop\README.md:164`）。

**代价量级**：一次切换 = 整段历史按 miss 价重算一次。命中价约为输入价的 ~1/10，故 H token 历史的会话切一次 ≈ `0.9 × H × 输入价`；H=100K 时约等于 90K token 的额外计费，且**每次切换都重来**（切回原集合也一样，因为 declarations 又变了一次）。

### 5.4 避免代价的三条路（按推荐度）

1. **声明集恒定 + 调用时判定（推荐）**：会话开始时把「必备 ∪ 全局 ∪ 工作台全集」一次性声明，之后**永不增删**（tools 数组字节稳定 → 缓存始终全命中，schema 成本按 cache-read 价付，几乎免费）。切换工作台只改「准入判定」：
   - `ctx.tools.guard(guard)`（`dsh-tools\lib\index.js:649-651`）注册单调拒绝；guard 收到 `exec`，返回字符串即拒绝原因（`checkGuards`，`:657-662`）；拒绝结果落在 `pipeline.js:402-413`（`Error: <reason>`，isError）。
   - **注册位置**：`checkGuards` 遍历 `[this.guards.global, ...this.guards.chainLayers(exec.agent)]`（`index.js:658`）。插件在自己的（无 agent 作用域的）ctx 上注册 → 进 global 层 → **对所有 agent 生效**，这正是工作台要的：一次注册，按 `exec.agent.session` 判定即可，不必给每个 agent 挂一遍。
   - 或 `tools/pre-execute` waterfall（`pipeline.js:386`），返回 `{ kind: 'deny', reason }`。
   - 或 `ctx.tools.register(name, def, { when })`：`when(context)` **每步重算**（`index.js:542-572`，context = `{ agent, modelSelection, signal }`），返回 false 即不可见 —— 但**这会让 schema 从 declarations 里消失**，等价于删除工具，仍然破坏缓存。**做工作台请用 guard，不要用 `when`。**
2. **只增不减 + `defer_loading`**：工作台只允许「加」，退场工具保留声明但 guard 拒绝。可保住前缀，代价是 schema 常驻。
3. **接受代价**：如果切换频率低（一个会话切 1–2 次）且历史不长（<20K token），直接改声明集最简单，不必优化。

## 6. 工具定义占多少 token

### 6.1 现成的估算函数（精确可用）

`@deepseek-ai/dsh-token-meter/estimate`（package.json `exports["./estimate"]`）：

```js
// lib/types/estimate.js
const CHARS_PER_TOKEN = 4;
const BLOCK_OVERHEAD = 4;
export const ROLE_OVERHEAD = 4;

export function estimateToolsTokens(header) {          // header.tools 是 canonical request header 的 tools
  if (header?.tools === undefined || header.tools.length === 0) return 0;
  return Math.ceil(JSON.stringify(header.tools).length / CHARS_PER_TOKEN) + BLOCK_OVERHEAD;
}
export function estimateMessage(message) { ... }
export function estimateContent(blocks) { ... }
export function estimateSystemMessage(message) { ... }
```

服务侧：`ctx.tokenMeter.measure(session, requestHeader?) → { totalTokens, surfaceTokens, nodes[] }`；`ctx.tokenMeter.estimateMessage(message)`；`ctx.tokenMeter.contextPressure(session)`。
投影：`contextBreakdown = { systemTokens, toolsTokens, messageTokens }`（`lib\index.js:227` 用 `estimateToolsTokens(canonicalHeader(event.data.header))` 计算，**跟随最新 `request/header`**），另有 `tokenUsage = { uncachedInputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`。

直接在插件里量当前会话的工具成本：

```js
const breakdown = session.projections.faceOf('contextBreakdown');   // { systemTokens, toolsTokens, messageTokens }
```

### 6.2 实测量级（按 4 字符/token 折算源文件字面量）

- `bash` 工具（`dsh-tool-bash\lib\index.js:243-244` description 836 字符 ≈ **209 token**；`:495-529` parameters 段 1,660 源字符 ≈ **415 token**）→ 单工具 ≈ **620 token**。
- `ask_user_question`（`dsh-tool-ask-user\lib\index.js:67-82`）定义体 420 字符 ≈ 105 token + 描述变量 → 约 **150–250 token**。
- 结论：**每工具 100–700 token，中位 200–400**；40 个工具 ≈ **8–16K token**，且这部分**每个请求都重复**（`dsh-system-prompt\README.md:166`：「Schema tokens repeat on every request」）。
- 注意低估：`estimate.js` 的注释与 README 都说明这是「fixed text-density estimate」，CJK 与 JSON schema 会被明显低估（真实分词器下 schema 往往高 1.2–1.5×）。

## 7. 子 agent 继承哪些工具

### 7.1 组合方式（`dsh-subagent\lib\types\child-agent.js`）

```js
// :140-152
function applyChildComposition(childCtx, parent, composition) {
  if (composition.agentPreset !== undefined) {
    const presets = childCtx.get('agentPresets');
    if (presets === undefined) throw new SubagentError('...requires the agent-presets service', 'PRESET_UNAVAILABLE');
    return presets.mount(childCtx, composition.agentPreset).then(() => { applyChildOverrides(childCtx, composition); });
  }
  childCtx.get('agentPresets')?.composeFrom(childCtx, parent.ctx);   // ← 继承父的 composition
  applyChildOverrides(childCtx, composition);
}

// :153-168
function applyChildOverrides(childCtx, composition) {
  childCtx.systemPrompt.context({ name: 'subagent:delegation', ... });
  if (composition.persona !== undefined) childCtx.systemPrompt.section({ name: 'deployment:persona-prefix', ... });
  if (composition.toolFilter !== undefined) childCtx.tools.restrict(composition.toolFilter);   // ← 显式 mask
}
```

- **继承**：父 preset 的 composition（`composeFrom(childCtx, parent.ctx)`），即 preset 挂载的那些工具注册；
- **不继承**：父 agent 自己用 `agentCtx.tools.restrict()` 加的 mask。作用域链里只有 preset registry 调 `bindScopeParent`（`registry\lib\index.js:686` `parent: bindScopeParent(key, generation.key)`），**agent 作用域之间不互链**（`dsh-scope\lib\index.js:239-269`）。所以父的 restrict 落在父自己的层，子 agent 的 `chainLayers(child)` 看不到。旁证：`applyChildComposition` 必须显式 `composeFrom` 重挂一遍 —— 如果 ctx 父子会传递注册，这一步就是多余的。
- **可显式传入**：子 agent 的 `composition.toolFilter = { allow?, deny? }`（`child-agent.js:167`、`manager.js:1217-1233` 从持久 descriptor 恢复；`dsh-tool-subagent\lib\index.js:591-667` 校验与序列化）。注意 `persona`/`toolFilter` 是 spawn 参数，**不能**写在插件 config 里（`tool-subagent\index.js:346` 直接抛错）。

### 7.2 能不能让子 agent 用同一套工作台

**能，而且做法和 §5.4 一致**：把工作台判定放在**调用期**（`ctx.tools.guard()` 或 `tools/pre-execute`），它天然对每个 agent 生效（`checkGuards` 按 `exec.agent` 走 `chainLayers`）。在 guard 里读 `exec.agent.session`：

- 子会话 → 读它自己的 `workbench` 投影；没有则回退到 `parentSession` 的选择（`childSessionMeta` 里已有 `parentSession` 字段，`child-agent.js:107-121`）。
- 若用 `restrict`/`when` 来实现白名单，则**子 agent 不会继承父的 mask**，必须在 `agent/created` 时给子 agent 重新挂一次，或走 `composition.toolFilter`。

| 决策点 | 建议 | 依据 |
|---|---|---|
| 选择存哪 | 会话事件 `workbench/selected` + Session projection `workbench` | §1.3、§3(a) |
| 读当前选择 | host：`handle.stateOf(session)`；客户端：`projections.faceOf('workbench')` | §4 |
| 客户端交互 | 仿 `session/selectModel`：`@Remote('selectWorkbench')` + 投影 wire view | §1.1-1.5 |
| 工具可见性 | **声明集恒定**，用 `ctx.tools.guard()` 拒绝非白名单调用 | §5.4 |

## 不确定处（明确标注，未臆测）

1. `deepseek-flash` 的 `defer_loading` 是否**真的**让服务端把新增 schema 排除在前缀之外，README 只说「tool-schema change still prevents reuse from the first altered token」，没有正面承诺「新增（deferred）不失效」。DSH 自身用 `addition-only`+`defer_loading`+in-history `tool_addition` 三件套显然是为此设计，但**建议实测**（打一次真实请求看 `cacheReadTokens`）后再当作定论。
2. `session.v4.jsonl.zstd` 是 zstd 压缩的，未解压核算真实 header 的 `toolsTokens`；§6.2 的数字按源码字面量以 4 字符/token 折算，是量级估计而非精确分词。
3. `@deepseek-ai/dsh-token-meter/estimate` 的子路径导出未在本机 node 里实测（运行环境无 `node_modules`），仅依据 `package.json` 的 `exports` 字段。
4. `agent/created` 的 `source` 除 `"startup"` 外的取值（如恢复/fork 的标记）未逐一确认；`register()` 传 `"startup"`，`resume()` 路径的 source 字符串未读到。
5. §5.1 的「tools 在前、messages 在后」是从 README 反推的**推断**，DSH 源码不体现服务端前缀顺序；若实际相反，则「删除/重排工具」的代价会小得多（只影响尾部），结论 §5.3 需相应下调。建议实测一次：固定历史，仅改一个工具定义，看 `cacheReadTokens` 是否归零。
6. `dsh-llm-deepseek\lib\index.js` 的 `toolUpdate` 归一化里，provider listing 的 `"leading-only"` 会被折成 `undefined`（`:2423`）——即某些 catalog 配置下 `addition-only` 语义会消失，工作台不要假设它一定存在。
